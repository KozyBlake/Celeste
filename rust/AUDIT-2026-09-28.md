# Java ↔ Rust divergence survey — 28 Sep 2026

Four parallel audits of the families PORTING.md still listed as "to diff",
run against the Java source rather than against the command surface. Each
entry names the Java site and the Rust site so it can be checked without
re-deriving the finding.

**Nothing in this file is fixed unless it says FIXED.** It is a work queue.

Scope audited: `vrchat-group` + VRChat search/ban/emoji; config & settings;
reports/history/info + the `ScarletData` store; the desktop UI.
Already-documented deliberate deviations were excluded by each audit.

## Fixed immediately (data loss)

### F1. `ScarletData` wrote snake_case where Java writes camelCase — FIXED

Java's Gson has no `FieldNamingPolicy` (`util/JsonAdapters.java`), so every
key is the Java field name verbatim: `userSnowflake`, `auditEntryIds`,
`guildSnowflake`, `entryTags`, `entryDescription`, `entryRedacted`,
`auxActorId`, … The Rust structs (`scarlet-core/src/data.rs`) carried no
`rename_all`, so they read and wrote snake_case.

Directory and file names matched, so a Java `global.json`, `live.json`,
`usr/<id>` or `gaud/<id>` was **found, deserialised as all-defaults, and
re-saved empty** — losing the Discord↔VRChat account-link table (which every
"linked ids" check reads), plus every tag, description, redaction flag and
evidence record.

Three maps needed explicit names rather than a blanket camelCase, because
Java spells them idiosyncratically: `userSnowflake2userId`,
`location2AuditEntryId`, `location2instanceEmbedMessage` (lower-case `i`).

Fixed with `rename_all = "camelCase"` plus those three renames, snake_case
`alias`es so files written by Rust builds during the port still load, and
three tests pinning the wire shape.

## High impact

### A1. Group owners are locked out of their own group's commands — FIXED
Java's `checkMemberAndSelfPerms` passes the actor when their linked VRChat id
equals `vrc.groupOwnerId`, independently of the role check
(`ScarletDiscordCommands.java:2568`). Rust's `moderation_context` only calls
the strict `user_has_group_permission` (`commands/mod.rs:642`). This is a
*second* owner check, at the command layer — distinct from the permission-helper
split fixed in pass 1, and dropped along with it. Affects all 15 gated
`vrchat-group` subcommands.

### A2. `set-audit-aux-webhooks` select submit has no permission check — FIXED
Java gates the string-select on MANAGE_SERVER/ADMINISTRATOR via
`checkConfigAccess` (`ScarletDiscordUI.java:2065`). Rust's
`handle_audit_aux_webhooks` (`interactions.rs:902`) has none, and the id is on
the default-allowed StringSelect list (`permissions.rs:315`), so any member can
rewrite audit routing.

### A3. `/query-target-history` leaks a redacted moderator's description — FIXED
Java only substitutes when the description contains the actor name, and
otherwise **discards the description entirely** for a canned sentence
(`ScarletDiscordCommands.java:3205-3212`). Rust does
`description.replace(actor_name, "a moderator")` (`moderation_history.rs:176-183`),
a no-op when the name isn't literally present — printing the original text.
Redaction is the whole point of that command.

### A4. Advisory row colouring is computed and never used — FIXED
Java repaints each row from the advisory — `text_color` as foreground, amber
fg+bg for flagged pronouns (`ScarletUI.java:762-813`). Rust computes
`text_color`/`pronouns_flagged` in core and `app.rs` never reads either
(`scarlet-ui/src/app.rs:398-467`). Watched users/groups/avatars don't visually
stand out, which is what the advisory pipeline exists for.

### A5. Audit event-type options have neither choices nor autocomplete — FIXED
Java gives `audit-event-type` inline choices when ≤25 values and autocomplete
above that (`ScarletDiscordCommands.java:257-258`, `DInteractions.java:1078-1083`).
Rust registers a bare required String (`set_event_channel.rs:146-156`,
`aux_webhooks.rs:64-75`), so the user must type e.g.
`groupex.instance.user.pedestal` verbatim.

Rust now follows the same cutoff: the 21 extended event types are labeled
inline choices, while the 34 audit event types use labeled autocomplete for
all routing commands and `/set-audit-aux-webhooks`.

### A6. `/scarlet-discord-permissions` can no longer be delegated — FIXED
Java registers it with no `default_member_permissions`, relying on DPerms, so
an admin can grant it to a role (`DPerms.java:126-130`). Rust sets
`ADMINISTRATOR` on the command *and* re-checks admin inside `run`
(`discord_permissions.rs:83,137`) — an inherited `slash-command … = Allow`
silently stops working.

Rust now leaves Discord's default member permissions unrestricted and relies
on the shared DPerms dispatch check, matching Java. A regression test also
proves an explicit role rule delegates the command to a non-administrator.

## Medium impact

### B1. Generic denial text on every `vrchat-group` subcommand — FIXED
Java: "You need the VRChat group permission `group-bans-manage` to list group
bans." (`:2572`). Rust falls back to the generic sentence because
`moderation_context` passes `denial_action: None` (`mod.rs:603-608`). Same gap
pass 1 closed for ban/unban.

### B2. `/settings edit` hides valid values
Java renders booleans/enums/choices as pre-selected `StringSelectMenu`s,
paginating past 25 (`:3519-3521`, `:3605-3610`). Rust emits one free-text input
whose "One of: …" label truncates at 45 chars (`settings.rs:151-199`).

### B3. `/settings` modal id changed, breaking carried-over permissions — FIXED
Java `"settings:"+id`; Rust `"settings-edit:"+id` (`settings.rs:15`). DPerms
keys modal-submit permissions on the text before the first `:`
(`DPerms.java:565`), so an existing `discord_perms.json` entry stops matching.

Restored Java's `settings:<id>` id and pinned the operation prefix in a test,
so existing modal-submit rules apply again.

### B4. String-array settings split on commas — FIXED
Java splits on line breaks only (`value.split("\\R")`, `:3815`). Rust joins
lines with `,` and then splits on `,` (`interactions.rs:1653`,
`file_valued.rs:263-271`), so any entry containing a comma (a URL with a query
string) is silently split in two.

`FileValued<Vec<String>>` now uses the Java newline representation end to end;
the modal no longer converts it through commas, and a regression test preserves
a comma-bearing URL as one entry.

### B5. No click-to-sort on table headers — FIXED
Java's `JTable` has a row sorter plus a "Default order" header popup
(`util/PropsTable.java:71,82,868`). Rust headers are drag-to-reorder only
(`app.rs:505-519`), so sorting by Acc-Age, Rank or Joined is gone.

Sortable Rust headers now toggle ascending/descending order and show a sort
marker. Right-clicking any header offers Java's "Default order" reset, while
the four Action-valued columns remain non-sortable like `PropsTable`.

### B6. Column layout isn't persisted, and `Unban`/`Invite` are missing — FIXED
Java saves each column's index, width and enabled flag to
`ui_instance_columns` every 10s (`ScarletUI.java:1338-1372`) and registers 17
properties, `Unban` and `Invite` hidden by default and toggleable
(`:708-709,834-836`). Rust has 15 always-visible columns reset every launch
(`app.rs:64-80,194-196`). Note PORTING.md:23 claims Java doesn't persist order
— that claim is wrong and should be corrected.

Rust now reads and writes Java's `ui_instance_columns` object, including
display index, width, and hidden state. The header menu toggles all 17 Java
columns; Unban and Invite start hidden and call the shared VRChat client when
enabled.

### B7. No re-sort after a live player update — FIXED
Java's `playerUpdate` calls `fireSort()` on every update
(`ScarletUI.java:306-311`). Rust only sorts on join/leave/catch-up
(`scarlet-events/src/listener.rs:703-705`), so someone who *switches into* a
watched avatar keeps their old row position.

### B8. TTS ignores the system output device — FIXED
Java synthesizes to WAV and plays it through `pw-play`/`paplay`/`aplay`
(overridable via `scarlet.tts.player` / `SCARLET_TTS_PLAYER`), specifically so
playback appears in the volume mixer and follows the selected device
(`util/tts/TtsService.java:351-358,404-415,591-598`). Rust spawns
`espeak-ng`/`spd-say`/`flite` directly with no player stage
(`scarlet-ui/src/tts.rs:25-31,55-100`) — the likely cause of the
"TTS goes to the wrong device" complaint, separate from the route switch
(which is correct).

Separately, and fixed: every failure on the *Discord* voice route was
silent. A missing `guildSf` or `audioChannelSf` hit a bare `continue`, so an
unconfigured voice channel was indistinguishable from working TTS that never
spoke. Each drop now names its cause once (not once per announcement),
surfaces in the status bar, and an empty synthesizer output is caught rather
than played as silence. The external-player stage is now ported too: on Linux eSpeak renders to a
WAV which is played through `pw-play`/`paplay`/`aplay`, overridable with
`CELESTE_TTS_PLAYER` (or Java's `SCARLET_TTS_PLAYER`), falling back to
letting the engine play directly when no player is on PATH — the same
fallback shape as Java's drop to Java Sound.

### B9. No exit confirmation or ordered shutdown — FIXED
Java uses `DO_NOTHING_ON_CLOSE` plus a yes/no prompt before `scarlet.stop()`
(`ScarletUI.java:1281-1288,1391-1401`). Rust installs no close handler, so the
X kills a running session outright.

### B10. `/vrchat-user-info` evidence lines drop three of four clauses — FIXED
Java renders file, proxy, linked audit entry, submitter and timestamp
(`:2092-2118`); Rust emits only filename and proxy (`vrchat_user_info.rs:86-96`).

Rust now renders every Java clause and returns Java's explicit “no metadata
found” response instead of posting a bare header for a newly seen user id.

### B11. `/discord-user-info` reads the wrong member's roles — FIXED
Java resolves permission-role mentions from the **invoker**'s roles
(`:3138-3143`); Rust uses the **target**'s (`discord_user_info.rs:23,64`).
Java's behaviour looks like a bug, but the visible answer differs.

Rust now deliberately uses the invoking interaction member's roles, matching
the reference behavior exactly.

### B12. `close-instance` has an extra bot-side gate Java lacks — FIXED
Java checks only the member's `group_instance_manage` (`:3045`); Rust also
requires Celeste's own account to hold it (`vrchat_group.rs:1631`).

### B13. `transfer-check` reports absent requirement flags as failures — FIXED
Java reads them as nullable and renders "Unknown" (`:2925`); Rust's fields are
plain `bool` with `serde(default)` (`models.rs:330-340`), so a field VRChat
didn't return shows as "No".

The five requirement fields are now `Option<bool>`, with Java's
Unknown/Yes/No rendering and a mock-response regression test for omission.

### B14. `ui_show_cli_tab` does nothing — FIXED
Registered (`settings/mod.rs:318`) but `tab_bar` renders all three tabs
unconditionally (`app.rs:377-383`).

### B15. Window geometry is never restored — FIXED
Java persists frame bounds on move/resize (`ScarletUI.java:1290-1305`); Rust
defines the setting and never reads or writes it.

Rust now opens at Java's `(100, 100, 600, 400)` default, restores `uiBounds`
when present, and updates the same registry key only when the native window
position or size changes.

## Low impact / cosmetic

- **FIXED — `add-role`/`remove-role` printed the raw role id** instead of the role name,
  and claim completion in past tense where Java hedges (`vrchat_group.rs:673,639`
  vs `:3075,3081`).
- **FIXED — Option length caps were missing** on `announcement-title` (100),
  `announcement-text` (1000), `member-search` (100) — `create-post` did port
  its caps, so this is inconsistent within one file.
- **`/moderation-log` action titles** are re-derived rather than read from
  `GroupAuditType` (`moderation_history.rs:493,607-631`): "CalendarEvent Create"
  vs Java "Event Create", "Instance Announcement" vs "Announcement".
- **`/moderation-summary` counts invites Java never counts** — Java's query
  omits `group.invite.create`, so its 4th number is always 0
  (`ScarletDiscordJDA.java:3790` vs `moderation_reports.rs:140`). Rust is more
  useful but costs an extra API page-through.
- **`/export-log`**: errors remain ephemeral in Rust versus public in Java;
  **fixed:** the `file-name` option again autocompletes the latest 25 log
  names (`:4101-4102`).
- **FIXED — `/vrchat-user-info`** now has Java's "no metadata found" path
  (`:2058-2062`).
- **`/discord-user-info` bypasses the entity cache** — the 28 Sep caching pass
  missed this call site (`discord_user_info.rs:47`); should be `within_1_day()`.
- **Channel option types unpinned** — Java pins TEXT/VOICE/CATEGORY at
  registration (`:261-263`); Rust registers all three untyped, so the picker
  offers channels the handler then refuses.
- **FIXED — `/aux-webhooks remove`** again autocompletes configured webhook
  ids (`:4245-4248`).
- **Settings tab grouping** guesses sections by id prefix (`app.rs:857-879`)
  where Java has 19 explicitly ordered named sections (`ScarletUI.java:3872+`);
  `heuristicKickCount`, `timed_bans_enabled`, `outstandingPeriodDays` land in
  "Other". The code comment claiming Java had only a category sidebar is wrong.
- **Notification matrix flattened** — Java renders a per-event grid with
  TTS/Desktop columns (`ScarletUI.java:4158-4200`); Rust lists ~27 flat toggles.
- **No menu bar** — File/Edit/View/Help (`ScarletUI.java:819-930`) has no
  equivalent, so credits, diagnostics, and manual update/announcement/API-status
  checks are unreachable.
- **Clear Instance** has no confirmation where Java confirms (`:1031-1036`).
- **Joined/Left drop seconds**; **Acc-Age** prints zero components Java omits.
- Wording nits: `set-voice-channel` success text, `set-verification-auto-invite`
  error, `/set-discord-account-age-alert` echoing the choice label instead of
  Java's `formatDurationHuman` output, the ban-multi modal placeholder.
